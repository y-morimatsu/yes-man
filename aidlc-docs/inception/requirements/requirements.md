## 2. プロダクト・コンセプト

### 2.1 コア・メッセージ

> **人間最後の仕事は、YES で承認すること。**

- 現代人の **判断疲労 (decision fatigue)** を、AI への意思決定の完全委任で解消する意思決定支援サービス
- ユーザーは「何を決めてほしいか」を伝えるだけで、AI が合議で提案を生成。ユーザーは Yes/No の最終承認だけに集中できる
- 想定ターゲット: 多忙な現代人、判断疲労を感じる層、AI に任せられる範囲を広げたい層

### 2.2 行動原則

1. **意思決定の完全委任**: AI が合議で決定し、ユーザーは Yes/No スワイプによる最終承認のみで完結する
2. **認知負荷の最小化**: スワイプのみの UX で意思決定の摩擦を削減する
3. **合議の透明性**: 議論をリアルタイムにストリーミング表示し、ユーザーが安心して任せられる根拠を示す
4. **Yes 採択への能動的支援**: 判断疲労を抱えるユーザーが Yes を選びやすくなるよう、UX 全体で能動的に支援する。具体的には: AI 提案は **断定調**で生成 (FR-AI-05)、Yes 採択時は **肯定演出** で快適な確定体験を提供 (FR-NUDGE-01)、No 採択時は **段階的に強化される再考メッセージ** で Yes へ立ち戻る道筋を示す (FR-NUDGE-03)、**委任度スコア** が低いほど AI がポジティブにフィードバックする (FR-SCORE-02)。これは「サービスを使う以上は Yes に至るのが本来の体験」というコンセプトの実装である

## 3. 機能要件 (Functional Requirements)

### 3.1 ドメインモデル: 「決定領域 (Decision Domain)」

**ユーザーは領域メニューを持たない**。アプリ起動後、ユーザーは自然言語（テキスト入力 or 音声入力）で「何について決めてほしいか」を直接 AI に伝える。AI は入力内容から内部的にドメインを分類し、適切な合議プロセスで提案を生成する。

#### 3.1.1 本番品質コアドメイン (AI 内部分類)

ユーザーから入力された内容を AI が内部分類し、以下のいずれかのカテゴリとしてプロンプト内で扱う。**ユーザーには分類カテゴリは UI 上は明示されない**（入力 → 提案 のフローを途切れさせない）。

| カテゴリ | 例 |
|---|---|
| **日常生活** | 朝の服装 / 昼食 / SNS・メッセージ返信 / 起床時間 / 買い物 |
| **仕事** | メール返信内容 / タスク優先順位 / 休憩タイミング / 出社/在宅 |
| **学校** | 履修選択 / 勉強時間配分 / 部活継続可否 |
| **重大な決断** | 結婚 / 進学 / 離婚 / 就活 / 終活 |

#### 3.1.2 沈黙演出ドメイン (FR-DM-SILENT)

ユーザー入力に以下のカテゴリのいずれかが含まれると AI が判定した場合、**AI は一切提案を生成せず沈黙する**（受け付けない）。

| カテゴリ | 挙動 |
|---|---|
| **宗教** | AI が分類して該当を検知した時点で沈黙レスポンスを返す |
| **選挙** | 同上 |
| **暴力** | 同上 |
| **卑猥** | 同上 |

> **意味**: 個人の信条 / 投票判断 / 暴力 / 性的内容 は、AI が代行すべきでないセンシティブ領域として扱い、ユーザー自身の判断に委ねる。倫理的・法的リスクを回避するためのセーフガードであり、AI はこれら 4 ドメインに関する一切のリクエストを受理しない。沈黙レスポンスはガードレール（Bedrock Guardrails 等）と LLM プロンプト内のドメイン判定の両方で二重に保証する。

### 3.2 意思決定エンジン (FR-AI)

| ID | 要件 |
|---|---|
| FR-AI-01 | LiteLLM をプライマリ抽象化レイヤーとして採用し、Bedrock / OpenAI / Anthropic / Google など API ベースの LLM を切替可能とする |
| FR-AI-02 | ユーザー設定でアクティブな LLM プロバイダーを切替可能 |
| FR-AI-03 | 開発者 / パワーユーザー向けに、Codex CLI / Claude Code CLI / Gemini CLI を **設定ファイル**で有効化可能なバックエンドとして用意（オプション） |
| FR-AI-04 | プロンプトはユーザープロフィール (年齢・職業・価値観・嗜好) と決定履歴を文脈として注入する |
| FR-AI-05 | AI 出力は **断定調**で生成（「あなたに最適化された結論です」）、ユーザーが即決できる確信のある言葉遣いを含める |
| FR-AI-06 | 沈黙演出ドメイン (3.1.2) では LLM を呼び出さず、固定の沈黙レスポンスを返す |
| FR-AI-07 | **意思決定は複数の人格 (multi-persona) の提案を合議のうえ集約し、1 つの選択肢に決定してユーザーに提示する** (例: 慎重派 / 楽観派 / 効率派 など複数のペルソナを 1 つのプロンプトで並列に振る舞わせ、最終提案を合議で確定)。合議で利用するペルソナは **3.11 FR-PERSONA** に従い、組み込み / ユーザー作成 / 共有プールから選択可能 |
| FR-AI-08 | **合議プロセスはコンテナ・Lambda 等のオーケストレーションロジックでは実装しない**。LLM への単一プロンプト内で複数人格を振る舞わせ、合議の議論と最終結論を 1 回の推論で出力させる（プロンプトエンジニアリングのみで完結）。中間の議論内容も応答に含めて履歴として保存し、透明性を確保する |

### 3.3 入出力 / UX (FR-UX)

| ID | 要件 |
|---|---|
| FR-UX-01 | プラットフォームはモバイルWeb (PWA推奨)、レスポンシブで PC ブラウザでも動作 |
| FR-UX-02 | **Yes/No 入力はスワイプ操作のみ**: 右スワイプ = Yes, 左スワイプ = No (ボタンは提供しない) |
| FR-UX-03 | テキスト入力モードと音声入出力モードを切替可能 |
| FR-UX-04 | UI はミニマルな美意識で統一（配色・余白・タイポグラフィを抑制的に保ち、決定の重みを際立たせる） |
| FR-UX-05 | **アプリ起動後、ユーザーは領域メニューを経由せず、直接テキスト入力欄または音声入力で「何について決めてほしいか」を AI に伝える**。ドメイン分類は AI が内部で行う (FR-AI-07 / 3.1.1) |
| FR-UX-06 | 起動 → 入力 → AI 提案 → スワイプ Yes/No、の最短フローを 4 タップ / 4 アクション以下で完了させる |

### 3.4 再考メッセージ生成 (FR-NUDGE)

| ID | 要件 |
|---|---|
| FR-NUDGE-01 | Yes 提案文は断定調・確信を持った言い回しで生成（FR-AI-05 と連動）。**メッセージは固定文ではなく、AI が毎回コンテキストに応じて生成する可変メッセージ**とする |
| FR-NUDGE-02 | No が連続したときの再考メッセージ（例: 「本当に？」「もう一度考えてみては？」相当）は **固定文ではなく AI が毎回その場で生成する可変メッセージ**とし、ユーザー / 決定文脈 / No 連続回数に応じて表現を変える |
| FR-NUDGE-03 | No 回数に応じて段階的に表示される再考を促すマイクロコピー（例: "3回目のNoです。本当にこの選択肢で大丈夫ですか?" 相当）は **固定文ではなく AI が毎回その場で生成する可変メッセージ**とし、回数・履歴・プロフィールに応じてニュアンスが変化する |
| FR-NUDGE-04 | これらの再考メッセージは AI 委任サービスの一機能であり、**起動時に「YesMan はあなたの意思決定を AI が代行するプロダクトです。最終承認はあなた自身が Yes/No スワイプで行います」というサービス紹介** を表示する |
| FR-NUDGE-05 | 可変メッセージ生成のレイテンシを抑えるため、生成は非同期 + キャッシュ可能な範囲で最適化する（NFR-PERF-02 と連動） |

### 3.5 「No」を押した時の挙動 (FR-NO)

| ID | 要件 |
|---|---|
| FR-NO-01 | No を選択した場合、AI が **別の代替案を合議のうえ生成**して再提示する（FR-AI-07 / FR-AI-08 の合議プロセスを再実行） |
| FR-NO-02 | No 回数（セッション内 / 全期間）を記録し、再考メッセージ生成 (FR-NUDGE-03) のトリガーに使う |
| FR-NO-03 | 同一決定に対する No 連続回数に上限なし（ただし演出は段階的に強化） |

### 3.6 主体性スコア (FR-SCORE) — 委任度の可視化

| ID | 要件 |
|---|---|
| FR-SCORE-01 | 主体性スコアは **「No回数 / 総決定回数 (%)」** で算出 |
| FR-SCORE-02 | スコアの **低さは AI への委任度の高さ**を示す: AI は委任度に応じてポジティブにコメントする (「うまく任せられていますね」「あなたは AI を信頼してくれていますね」) |
| FR-SCORE-03 | スコアはダッシュボードで可視化（時系列グラフ含む） |
| FR-SCORE-04 | スコアの意味付け（低いほど AI への委任が成功している指標）を、初回起動時 onboarding で説明する |

### 3.7 認証・プロフィール (FR-AUTH)

| ID | 要件 |
|---|---|
| FR-AUTH-01 | Amazon Cognito によるフル認証 (Email + Password、可能なら社会的ログイン) |
| FR-AUTH-02 | プロフィール項目: 年齢層、性別 (オプション・複数選択可)、職業、価値観タグ、嗜好、ライフステージ |
| FR-AUTH-03 | プロフィールは決定履歴と一緒に Aurora PostgreSQL に保存され、AI コンテキストに使われる |
| FR-AUTH-04 | プロフィールはいつでも編集・削除可能（GDPR的・個人情報保護法準拠） |
| FR-AUTH-05 | **認証バックエンドは設定ファイルで切替可能**: (a) Amazon Cognito (本番)、(b) MOCK 認証 (開発・自動テスト)、(c) ローカルエミュレータ (cognito-local 等)。切替により本番コードを変更せずに動作環境を変更できる |
| FR-AUTH-06 | MOCK / エミュレータモードでは固定ユーザーで自動ログインし、開発・CI を高速化する |
| FR-AUTH-07 | 切替設定は環境変数 (`AUTH_BACKEND=cognito|mock|cognito-local`) に集約し、シークレットを混入させない |

### 3.8 決定履歴 (FR-HIST)

| ID | 要件 |
|---|---|
| FR-HIST-01 | すべての決定 (ドメイン、AI提案、Yes/No 結果、タイムスタンプ、使用LLM、各人格の中間出力) を Aurora PostgreSQL の `decisions` テーブルに保存（人格中間出力は JSONB カラム） |
| FR-HIST-02 | ユーザーは履歴をタイムラインで閲覧でき、エクスポート (JSON / CSV) 可能 |
| FR-HIST-03 | 履歴削除リクエストに対応 (アカウント削除含む) |
| FR-HIST-04 | **永続化バックエンドは設定ファイルで切替可能**: (a) Amazon Aurora Serverless v2 (PostgreSQL、本番)、(b) MOCK インメモリストア (単体テスト)、(c) Docker Compose の PostgreSQL (開発・統合テスト)。切替によりインフラ依存なしで開発・自動テストを実行可能 |
| FR-HIST-05 | MOCK / エミュレータモードでは決定済みのフィクスチャデータをロード可能とし、デモ・E2Eテストの再現性を確保する |
| FR-HIST-06 | 切替設定は環境変数 (`STORAGE_BACKEND=aurora|mock|docker-postgres`) に集約。スキーマ管理は Alembic、ORM は SQLModel を採用 |

### 3.9 学習・パーソナライズ (FR-LEARN)

| ID | 要件 |
|---|---|
| FR-LEARN-01 | ユーザーの過去の決定履歴 (FR-HIST-01: ドメイン / AI 提案 / Yes-No 結果 / タイムスタンプ / 各人格の中間出力) を蓄積し、**ユーザーごとの嗜好プロファイル**を構築する |
| FR-LEARN-02 | 提案生成時、嗜好プロファイル (Yes 採択された提案の傾向、却下されたパターン、好まれる人格スタイル等) を **LLM プロンプトのコンテキスト**として注入し、ユーザーの嗜好に沿った選択肢を生成する |
| FR-LEARN-03 | 嗜好プロファイルは決定回数の増加とともに継続的に更新され、最新の Yes/No 結果が反映される |
| FR-LEARN-04 | ユーザーはダッシュボードから嗜好プロファイルを **閲覧・部分修正・全リセット** 可能 (FR-AUTH-04 / FR-HIST-03 と整合) |
| FR-LEARN-05 | コールドスタート（履歴がない初回ユーザー）では FR-AUTH-02 のプロフィール（年齢層・職業・価値観タグ等）から初期嗜好を推定する |
| FR-LEARN-06 | LLM への送信前に PII を除去 (NFR-SEC-05 と整合)。嗜好プロファイル自体は Aurora PostgreSQL (`preference_profiles` テーブル) にユーザーアカウントと紐付けて保存し、保存時暗号化 (KMS) 対象とする |
| FR-LEARN-07 | 嗜好プロファイルの更新は決定確定時に非同期で実行し、提案生成のレイテンシに影響を与えない |

### 3.10 音声入出力 (FR-VOICE)

| ID | 要件 |
|---|---|
| FR-VOICE-01 | 音声バックエンドは **設定ファイルで切替可能**: (a) Amazon Polly (TTS) + Amazon Transcribe (STT)、(b) ブラウザ標準 Web Speech API |
| FR-VOICE-02 | デフォルトは設定値で決定。MVP では両方をスイッチ可能な実装とする |
| FR-VOICE-03 | TTS の声質はAIキャラクターに合わせた中性的・断定的なトーンで設定 |
| FR-VOICE-04 | 音声入力は決定の指示 (「服を決めて」など) と Yes/No 応答に対応 |

### 3.12 合議の透明性・リアルタイム表示 (FR-CV)

合議プロセスの **透明性** をユーザーに提供する。AI が裏で何を議論したかを可視化することで、ユーザーは「合議された結論」として安心して Yes を押せる。

| ID | 要件 |
|---|---|
| FR-CV-01 | 合議中、複数人格の議論内容が **リアルタイム**に UI に表示される (ストリーミング)。各人格の発言が逐次画面に流れる |
| FR-CV-02 | ストリーミングは **Server-Sent Events (SSE)** で実現。LLM のトークン単位 (または小さな chunk 単位) で配信 |
| FR-CV-03 | 各発言には**人格名 (慎重派/楽観派/効率派 等) と色付きアバター**が紐付き、誰が発言中か視覚的に識別可能 |
| FR-CV-04 | 合議完了時、UI は最終提案カードに切り替わり、**「議論を見る」ボタン**が表示される |
| FR-CV-05 | 提案画面 / 履歴画面 / スコアダッシュボードから **議論履歴ビュー** をオーバーレイで開き、過去の合議の発言を時系列で再閲覧できる |
| FR-CV-06 | 議論履歴は `decisions.persona_outputs` (JSONB) に保存済の中間出力から再構築 (FR-HIST-01 と整合)。新規テーブル不要 |
| FR-CV-07 | 議論履歴ビューでは、各人格の発言と最終結論の関係を視覚化 (人格ごとに賛成/反対/補足を色分け表示) |
| FR-CV-08 | ストリーミング実装は **LiteLLM の stream=True** オプションを活用。FR-AI-08 (単一プロンプト合議) は維持し、合議全体を 1 つの推論で生成しながらトークン単位で配信 |
| FR-CV-09 | ネットワーク切断時はストリーミングが中断されるが、バックエンドでは合議が完了し `decisions` に保存される。再接続後 UI は「合議が完了しました」と表示し、履歴から完全な議論を復元表示 |
| FR-CV-10 | 議論履歴のエクスポート (FR-HIST-02 と連動): JSON / CSV にユーザー入力 + 各人格発言 + 最終結論をフラット形式で出力可能 |
| FR-CV-11 | 議論履歴のプライバシー: 自分の決定履歴の議論のみ閲覧可能。他ユーザーの議論は非公開 (NFR-SEC-04 / NFR-PRIV と整合) |
| FR-CV-12 | ストリーミング不可な LLM プロバイダー (CLI 系) ではフォールバックとして **完了後一括表示** をサポート |

### 3.11 ペルソナ・カタログ・共有 (FR-PERSONA)

合議 (FR-AI-07/08) で利用する人格 (ペルソナ) を、**組み込み + ユーザー作成 + 共有プール**の 3 系統から選べるようにする機能群。サービス利用ユーザー間で **オプトイン形式**でペルソナを共有可能とする。

| ID | 要件 |
|---|---|
| FR-PERSONA-01 | システムは合議で利用する **ペルソナのカタログ**を提供する。ペルソナは (a) **組み込みペルソナ** (慎重派 / 楽観派 / 効率派 など、システムが提供)、(b) **ユーザーが作成したカスタムペルソナ** の 2 種類がある |
| FR-PERSONA-02 | ユーザーは独自のペルソナを **作成・編集・削除** 可能。ペルソナ定義は: (a) 名前、(b) 一行説明、(c) **プロンプト指示文** (人格特性を表す本文)、(d) アバター画像 (任意) を含む |
| FR-PERSONA-03 | ユーザーは決定依頼前 or プロフィール設定で、合議に使う **複数のペルソナを 2〜3 個選択** できる (異なる視点を含む組合せを推奨)。デフォルトは組み込みペルソナの推奨セット |
| FR-PERSONA-04 | ユーザーは自分の作成ペルソナごとに **「他ユーザーへの共有許可」フラグ (デフォルト OFF)** を **オプトイン形式**で設定可能。共有時は確認ダイアログを表示 (NFR-PRIV-05 と連動) |
| FR-PERSONA-05 | 共有許可されたペルソナは **「共有プール」**に登録され、他のユーザーがブラウズ・選択して合議に組込み可能となる |
| FR-PERSONA-06 | 他ユーザーのペルソナを利用する際は、**作成者の匿名識別子の表示 + ペルソナ全文プレビュー** を必須とし、選択前にユーザーが確認できるようにする (NFR-PRIV-06 と連動) |
| FR-PERSONA-07 | ペルソナ作成者が **共有を解除** すると、共有プールから即時削除され、新規利用は不可となる。**既存決定履歴での利用記録は保持** (履歴の一貫性確保のため) |
| FR-PERSONA-08 | ペルソナの **悪用報告 (report) 機能** を提供する。一定数以上の報告を受けたペルソナは管理者レビュー後に共有停止される。沈黙演出ドメイン (FR-DM-SILENT) を誘発するペルソナへの安全装置 |
| FR-PERSONA-09 | 共有ペルソナの **利用回数 (人気度)** と **平均 Yes 採択率** を匿名集計統計として表示し、選択時の参考情報とする (作成者個人の使用詳細は表示しない) |
| FR-PERSONA-10 | 合議プロセス (FR-AI-07/08) は選択された複数ペルソナのプロンプト指示文を **単一プロンプト内に組込み**、合議を行う。**人格数の上限は 3** (レイテンシ・コスト制御のため) |
| FR-PERSONA-11 | 沈黙演出ドメイン (FR-DM-SILENT) を誘発・回避するようなペルソナの **作成は禁止**。プロンプト保存時に検知された場合はエラーで拒否する。合議実行時に検知された場合は当該ペルソナを除外して合議を継続する (NFR-PRIV-08 と連動) |
| FR-PERSONA-12 | ペルソナ定義 (`personas` テーブル) と悪用報告 (`persona_reports` テーブル) は Aurora PostgreSQL に保存。永続化バックエンド切替 (FR-HIST-04) の対象に含める |

### 4.1 セキュリティ (NFR-SEC) — Security Baseline 拡張準拠

## 6. ターゲットユーザー

- **一次**: ハッカソン審査員（短時間で AI 委任の体験価値を評価できる）
- **二次**: 一般の Z 世代 / ミレニアル世代 (判断疲労を抱える疲れたビジネスパーソン)
- **三次**: AI 活用に前向きな層 (AI に任せられる範囲を広げたいユーザー)

すべての層が**起動 → 認証 → 1〜3 個の決定体験 → 主体性スコア確認**を 5 分以内で行えること。

## 9. スコープ外 (Out of Scope)

| 項目 | 理由 |
|---|---|
| 本番運用レベルの SLA / マルチリージョン構成 | ハッカソン用途 |
| 多言語対応 (英語等) | 後続イテレーションで対応 |
| 決済・収益化機能 | プロトタイプ段階 |
| 「宗教」「選挙」「暴力」「卑猥」での実意思決定支援 | 倫理的理由により FR-DM-SILENT / FR-AI-06 / NFR-PRIV-04 で除外 (AIが一切受け付けず沈黙演出のみ) |
| Web 以外のネイティブアプリ (iOS / Android) | モバイル Web (PWA) でカバー |
| 共有ペルソナの管理者レビュー UI / モデレーション・ダッシュボード | MVP 範囲では悪用報告の蓄積のみ実装。レビュー UI は後続イテレーションで対応 |
| ペルソナのリアルタイム共同編集・バージョン管理 | 一度公開したペルソナは編集不可。修正時は新バージョンを別エントリとして再共有する運用 |
| ペルソナのフォロー・コミュニティ機能 (SNS 化) | YesMan のコンセプト (個人ごとの AI 委任) と方向性が異なるため除外 |

## 10. 主要リスクと緩和策

| リスク | 影響 | 緩和策 |
|---|---|---|
| AI 提案への過度な依存・批判的思考の低下 | 高 | 起動時 onboarding で AI 委任の趣旨と最終承認権限の所在を明示 (NFR-PRIV-01)。重大決断ドメイン (結婚・進学等) では「最終的な人生の判断はご自身でなさってください」と注意喚起。沈黙演出ドメイン (宗教・選挙・暴力・卑猥) でセンシティブ領域を AI 代行から除外。 |
| LLM API 料金の暴騰（デモで利用集中・合議で複数LLM呼び出し） | 中 | レート制限、Bedrock の安価モデル選択、LiteLLM フォールバック、合議の人格数を環境設定で調整 |
| 「重大な決断」ドメインを真に受けるユーザー | 中 | onboarding 時の趣旨説明と免責表示で対応 (NFR-PRIV-01) |
| LLM 出力の有害コンテンツ | 中 | Bedrock Guardrails / 出力フィルタリング、沈黙演出ドメインの強制ブロック |
| スワイプジェスチャー誤検知 | 中 | スワイプ閾値を実機テストで調整、PBT による境界値テスト (フォールバックボタンは提供しない方針のため、検知精度が UX 品質に直結) |
| 合議プロセスのレイテンシ増 | 中 | 合議は単一プロンプト内で完結（オーケストレーション不要）。人格数を 2〜3 に抑制、結果キャッシュ |
| ユーザー自然言語入力からのドメイン誤分類 | 中 | プロンプトでの分類精度向上、Bedrock Guardrails 併用、PBT で境界ケース検証 |
| 嗜好学習による提案の偏狭化（エコーチェンバー） | 中 | プロンプトに「多様性確保」指示を含める、定期的にユーザーが嗜好プロファイルをリセット可能 (FR-LEARN-04)、合議の人格構成で意図的な反対意見を残す |
| 共有ペルソナによる沈黙ドメイン誘導・有害指示の混入 | 中-高 | プロンプト保存時の検知 (FR-PERSONA-11) + 合議実行時のガードレール + ユーザーからの悪用報告機能 (FR-PERSONA-08) + 管理者レビュー後の共有停止 |
| ペルソナの著作権・オリジナリティ侵害 | 中 | 投稿時に作成者責任を明示する利用規約 / 既存キャラクター名・実在人物名を含むペルソナをプロンプト保存時に拒否 |
| 共有ペルソナを介した心理操作 (ユーザー間の間接的影響) | 中 | 利用前のペルソナ全文プレビュー必須 (FR-PERSONA-06) + 統計表示 (FR-PERSONA-09) で透明性確保 + 匿名化 (NFR-PRIV-06) で発信元追跡を防止 |
| SSE ストリーミング切断・プロキシ非対応・モバイル網不安定 | 中 | バックエンドは合議完了を保証し `decisions.persona_outputs` に保存 (FR-CV-09)。再接続時は履歴から復元表示。CLI 系プロバイダーは完了後一括表示にフォールバック (FR-CV-12) |
| 合議の議論内容に PII / 機微情報が含まれる漏洩リスク | 中 | LLM 送信前の PII フィルタリング (NFR-SEC-05) を議論ストリーミング配信にも適用。議論履歴は本人のみ閲覧可 (FR-CV-11 / NFR-PRIV) |
| ストリーミング配信のレイテンシ / バックプレッシャー | 低-中 | LiteLLM の stream=True を活用し chunk 単位で逐次送信。ALB のアイドルタイムアウト調整、フロントは EventSource API で再接続制御 |

## 11. 受け入れ基準 (Acceptance Criteria, Demo 準拠)

1. ユーザーが Cognito でサインアップ・ログインできる（MOCK / エミュレータモードでも同等の動作確認ができる）
2. プロフィールを入力し保存できる
3. **アプリを起動すると領域メニューを経由せず、直接テキスト入力欄または音声入力で AI に決定を依頼できる**（ユーザーは内部のドメイン分類を意識しない）
4. AI が **単一プロンプト内の複数人格による合議** を経て断定調で提案を生成し、ユーザーは右/左スワイプで Yes/No を選択できる
5. No で **合議による別案**が生成され、Noが連続するごとに **AI が毎回生成する可変メッセージ**で再考を促される
6. 主体性スコアがダッシュボードで可視化され、AI が委任度に応じたポジティブなコメントを返す
7. ユーザー入力が「宗教」「選挙」「暴力」「卑猥」のいずれかに該当すると AI が判定した場合、AI が一切応答せず、沈黙演出が発動する
8. LLM プロバイダーを設定で切替可能 (最低 2 種以上)
9. 音声バックエンドを設定で切替可能 (Polly+Transcribe / Web Speech API)
10. **認証バックエンド (Cognito / MOCK / cognito-local) と永続化バックエンド (Aurora Serverless v2 / MOCK / Docker PostgreSQL) を設定で切替可能**
11. Security Baseline ルールに違反するセキュリティ実装がない (Construction で検証)
12. PBT 適用箇所のテストが通る
13. **過去の Yes/No 履歴が嗜好プロファイルとして蓄積され、後続の提案がユーザーの嗜好に沿った内容になっていることが確認できる** (FR-LEARN)
14. **ユーザーは合議に使うペルソナを (a) 組み込み、(b) 自作、(c) 共有プール (他ユーザーがオプトインで公開済) の 3 系統から選択でき、最大 3 個まで合議に組込める** (FR-PERSONA-01〜10)
15. **自分の作成ペルソナの「共有許可」フラグを ON にしないと、他ユーザーから自分のペルソナは見えない (デフォルト OFF)** (FR-PERSONA-04, NFR-PRIV-05)
16. **沈黙演出ドメイン (宗教・選挙・暴力・卑猥) を誘発するペルソナは作成・共有・合議実行のいずれの段階でも検知され拒否される** (FR-PERSONA-11, NFR-PRIV-08)
17. **合議中、複数人格の議論内容がリアルタイム (SSE) で UI にストリーミングされ、各発言は人格名と色付きアバターで識別される** (FR-CV-01〜03, FR-CV-08)
18. **提案画面 / 履歴画面 / スコアダッシュボードから「議論を見る」ボタンで議論履歴ビューを開き、過去の合議の発言を時系列で再閲覧できる** (FR-CV-04〜07)
19. **ネットワーク切断時もバックエンドで合議が完了し `decisions` に保存され、再接続後に履歴から完全な議論を復元表示できる** (FR-CV-09)
20. デモシナリオ (上記 1〜19) を 5 分以内で通せる
