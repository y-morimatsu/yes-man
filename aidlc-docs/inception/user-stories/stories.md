# Journey A: オンボーディング

> 起動 → 趣旨説明（免責）→ サインアップ → プロフィール入力 → 初回提案

## Story A1: 起動時の趣旨説明と免責表示

**As a** 田中 涼介,
**I want** アプリを初回起動したときに YesMan が「AI が人間の主体性を奪う体験を演出する作品」であることを明示してもらいたい,
**so that** 後続の体験（再考マイクロコピー、断定調の提案）が AI 委任サービスの設計上の意図だと理解した上で利用できる.

**AC**:
```gherkin
Scenario: 初回起動時の趣旨説明表示
  Given アプリが端末に初めて起動された
  When スプラッシュ画面が完了する
  Then 「これは AI が人間の主体性を奪う体験を演出する作品です」という趣旨説明が全画面で表示される
  And 「主体性スコア (低いほど委任度が高い)」「沈黙演出 (4 ドメインは AI 代行外)」の意味付けについての注釈が含まれる
  And 「同意して始める」のスワイプ操作で次の画面に進める

Scenario: 2 回目以降の起動では趣旨説明をスキップ
  Given 初回起動時に趣旨説明を確認済みである
  When アプリを再起動する
  Then 趣旨説明全画面はスキップされ、サインイン画面に直接遷移する
```

## Story A2: サインアップ

**As a** 佐藤 美咲,
**I want** Email + Password で素早くサインアップしたい,
**so that** すぐに自分の決定を AI に委ねる体験を始められる.

**AC**:
```gherkin
Scenario: 新規ユーザーのサインアップ成功
  Given 趣旨説明を確認済みで、サインアップ画面にいる
  When 有効な Email と要件を満たすパスワードを入力して送信する
  Then アカウントが作成される
  And プロフィール初期入力画面に遷移する

Scenario: パスワード強度が要件を満たさない
  Given サインアップ画面にいる
  When パスワード強度が要件未満で送信する
  Then パスワード要件違反のエラーメッセージが表示される
  And アカウントは作成されない
```

## Story A3: プロフィール初期入力

**As a** 田中 涼介,
**I want** 年齢層・職業・価値観タグを最小限に入力したい,
**so that** AI が自分のコンテキストを踏まえて初回提案を行ってくれる.

**AC**:
```gherkin
Scenario: プロフィール最小項目入力で完了できる
  Given サインアップ直後のプロフィール入力画面にいる
  When 年齢層と職業のみ入力して保存する
  Then プロフィールがアカウントに紐付けて保存される
  And ホーム（決定依頼入力）画面に遷移する

Scenario: 任意項目をスキップしても進める
  Given プロフィール入力画面にいる
  When 価値観タグを未選択のまま保存する
  Then プロフィールは必須項目のみで保存される
  And ホーム画面に遷移する
```

## Story A4: 初回提案体験

**As a** 田中 涼介,
**I want** ログイン直後の初回入力で、合議された提案がすぐ返ってくる体験をしたい,
**so that** YesMan が何をしてくれるサービスなのかを 30 秒以内に理解できる.

**AC**:
```gherkin
Scenario: 初回入力に対し合議提案が表示される
  Given ホーム画面にプロフィール入力直後にいる
  When 「明日の朝食を決めて」とテキスト入力して送信する
  Then 5 秒以内に AI からの断定調の提案文が表示される
  And 提案文に複数人格の合議結果が反映されている
  And スワイプ Yes / No の入力エリアが提案直下に表示される
```

# Journey B: コア決定ループ

> 入力 → 合議 → 提案 → スワイプ → 結果保存 → スコア更新

## Story B1: テキスト入力で決定を依頼

**As a** 田中 涼介,
**I want** ホーム画面のテキスト入力欄に決めてほしいことを自然言語で書きたい,
**so that** 領域メニューを経由せず最短で AI に委ねられる.

**AC**:
```gherkin
Scenario: テキスト入力で AI が即座に提案を返す
  Given ホーム画面にテキスト入力モードでいる
  When 「今日のランチを決めて」と入力して送信する
  Then 入力内容がサーバーに送信される
  And ローディング演出が表示される
  And AI の提案が断定調で返る

Scenario: 空入力では送信できない
  Given ホーム画面にいる
  When 空文字または空白のみで送信を試みる
  Then 送信ボタンが押せない、または送信エラーが返る
```

---

## Story B2: 音声入力で決定を依頼

**As a** 佐藤 美咲,
**I want** マイクボタンを押して音声で決定を依頼したい,
**so that** 通勤中など手が塞がっているときも YesMan に委ねられる.

**AC**:
```gherkin
Scenario: 音声入力モードで決定を依頼できる
  Given ホーム画面で音声入力モードに切り替えた
  When マイクボタンを長押しして発話し、リリースする
  Then 発話内容が文字起こしされてプレビュー表示される
  And 確定スワイプで AI に送信される
  And 提案文が画面に表示される（読み上げ可能な場合は TTS で発話される）

Scenario: 音声バックエンドが設定で切り替わっている
  Given 音声バックエンド設定が Web Speech API に設定されている
  When 音声入力で決定を依頼する
  Then ブラウザの Web Speech API が使われる（Polly/Transcribe は呼ばれない）
```

---

## Story B3: AI が合議のうえ提案を生成する

**As a** 田中 涼介,
**I want** 提案が複数人格の合議を経て生成されたものであってほしい,
**so that** 軽率な単発回答ではなく「議論された結論」として安心して Yes できる.

**AC**:
```gherkin
Scenario: 単一プロンプト内の合議で 1 つの提案が返る
  Given 任意の決定依頼が入力された
  When AI が処理する
  Then LLM への呼び出しは単一プロンプトであり、Lambda オーケストレーションは経由していない
  And レスポンスには複数人格（慎重派 / 楽観派 / 効率派など）の議論ログと最終結論が含まれる
  And ユーザー画面には最終結論のみが断定調で表示される

Scenario: 議論ログは履歴に残る
  Given 合議による提案が表示された
  When ユーザーが履歴詳細を開く
  Then 各人格の中間出力が確認できる
```

---

## Story B4: スワイプで Yes/No を選択

**As a** 田中 涼介,
**I want** 提案に対して右/左スワイプで直感的に Yes/No を選びたい,
**so that** ボタンを探す手間なく決定をスキップできる.

**AC**:
```gherkin
Scenario: 右スワイプで Yes
  Given AI 提案が表示されている
  When ユーザーが右方向に閾値を超えてスワイプする
  Then 提案が Yes として確定する
  And 確定演出（肯定感を与えるアニメーション）が再生される

Scenario: 左スワイプで No
  Given AI 提案が表示されている
  When ユーザーが左方向に閾値を超えてスワイプする
  Then 提案が No として記録される
  And 別案再生成（Story C1）の処理に進む

Scenario: 閾値未満のスワイプはキャンセル
  Given AI 提案が表示されている
  When ユーザーが閾値未満で指を離す
  Then 提案カードは元の位置に戻る
```

---

## Story B5: 決定結果の永続化

**As a** 田中 涼介,
**I want** 自分の Yes/No と各人格の合議ログが保存されてほしい,
**so that** 後から履歴を振り返ったり、嗜好が学習されたりする.

**AC**:
```gherkin
Scenario: Yes 選択時に履歴が保存される
  Given スワイプで Yes が確定した
  When サーバーに送信される
  Then DynamoDB（または設定で MOCK / DynamoDB Local）に決定エントリが保存される
  And エントリにはドメイン分類 / 提案文 / Yes/No / タイムスタンプ / 使用 LLM / 各人格の中間出力が含まれる

Scenario: ネットワーク失敗時はリトライキューに入る
  Given スワイプ確定後にネットワーク障害が発生した
  When 保存リクエストが失敗する
  Then クライアント側のリトライキューに入り、復旧時に再送される
```

---

## Story B6: 主体性スコアの更新と表示

**As a** 田中 涼介,
**I want** 自分の主体性スコアがダッシュボードで可視化されてほしい,
**so that** どれだけ AI を信頼して任せられているかを定量的に把握できる.

**AC**:
```gherkin
Scenario: スコアが Yes/No 比で算出される
  Given ユーザーが少なくとも 1 件の決定履歴を持つ
  When ダッシュボードを開く
  Then スコアが「No 回数 / 総決定回数 (%)」で表示される
  And 時系列推移のグラフが表示される

Scenario: AI が委任度に応じてポジティブにコメントする
  Given スコアが 10% 未満（高い委任度）である
  When ダッシュボードを表示する
  Then 「うまく任せられていますね」「AI を信頼してくれていますね」相当のコメントが表示される
  And コメント文は固定文ではなく AI が毎回生成した可変文である
```

## Story B7: 合議中の議論をリアルタイムで閲覧する

**As a** 田中 涼介,
**I want** 提案が出るまでの合議の議論を、各人格の発言が画面に流れる形でリアルタイムに見たい,
**so that** AI が裏で何を議論しているかが透明に伝わり、「合議された結論」として安心して Yes を押せる.

> **追加日**: 2026-05-10 (要求仕様の追加 FR-CV: 合議の透明性・リアルタイム表示)

**AC**:
```gherkin
Scenario: 合議の発言が SSE で逐次表示される
  Given ホーム画面で決定依頼を送信した
  When バックエンドが合議推論を開始する
  Then ブラウザは Server-Sent Events (SSE) でストリーミングを受信する (FR-CV-02)
  And 各人格 (慎重派 / 楽観派 / 効率派など) の発言が時系列で画面に逐次描画される (FR-CV-01)
  And 各発言には人格名と色付きアバターが表示される (FR-CV-03)

Scenario: 合議完了で最終提案カードに切り替わる
  Given ストリーミングで合議が進行中
  When LLM が最終結論のトークンまで配信し終える
  Then UI は最終提案カードに切り替わる (FR-CV-04)
  And 最終提案カード上に「議論を見る」ボタンが表示される
  And スワイプ Yes/No 入力エリアが活性化される

Scenario: ネットワーク切断時もバックエンドで合議が完了し履歴から復元
  Given 合議ストリーミング中にネットワークが切断された
  When バックエンドは合議を最後まで完了し `decisions.persona_outputs` に保存する (FR-CV-09)
  And クライアントが再接続する
  Then UI は「合議が完了しました」と表示する
  And 履歴ビューから完全な議論を復元表示できる

Scenario: ストリーミング不可なプロバイダーは完了後に一括表示
  Given 環境変数 LLM_PROVIDER=cli-codex のようにストリーミング非対応バックエンドが選択されている
  When 決定依頼を送信する
  Then UI はローディング演出を表示し、合議完了後に発言を一括表示する (FR-CV-12)
  And 提案カード切り替えと「議論を見る」ボタンの挙動は通常時と同じ
```

## Story B8: 過去の合議の議論履歴を閲覧する

**As a** 田中 涼介,
**I want** 過去の決定について「議論を見る」から合議の発言を再閲覧したい,
**so that** 自分が Yes を押した判断の根拠を後から振り返れる.

> **追加日**: 2026-05-10 (要求仕様の追加 FR-CV: 議論履歴ビュー)

**AC**:
```gherkin
Scenario: 提案画面から議論履歴ビューを開く
  Given 最終提案カードに「議論を見る」ボタンが表示されている
  When ユーザーがそのボタンを押す
  Then 議論履歴ビューがオーバーレイで開く (FR-CV-05)
  And `decisions.persona_outputs` (JSONB) から発言が時系列で復元表示される (FR-CV-06、新規テーブル不要)
  And 各人格の発言と最終結論の関係が色分けで視覚化される (FR-CV-07、賛成 / 反対 / 補足)

Scenario: 履歴画面・スコアダッシュボードからも議論を再閲覧できる
  Given 履歴タイムライン画面 / スコアダッシュボードを開いている
  When 過去の決定エントリをタップする
  Then 議論履歴ビューがオーバーレイで開く (FR-CV-05)
  And 当該決定の発言と最終結論が表示される

Scenario: 議論を含めて履歴をエクスポートできる
  Given 履歴画面でエクスポートを選択する
  When エクスポート形式 (JSON / CSV) を指定して実行する
  Then ユーザー入力 + 各人格発言 + 最終結論がフラット形式で出力される (FR-CV-10、FR-HIST-02 と連動)

Scenario: 自分の決定の議論のみ閲覧可能
  Given 別ユーザーの decision_id を URL クエリで指定して議論履歴ビューを開く
  When サーバーが要求者の user_id と decisions.user_id を突合する
  Then 一致しない場合は 403 Forbidden が返される (FR-CV-11、NFR-SEC-04 / NFR-PRIV と整合)
```

# Journey C: No 連打体験

> 別案再生成 → 再考マイクロコピー → AI の問い直し → 最終的に Yes

## Story C1: No で合議による別案を再生成

**As a** 田中 涼介,
**I want** No を選んだら別の選択肢を AI が合議のうえ再提案してほしい,
**so that** 同じ提案で詰まらず体験が継続する.

**AC**:
```gherkin
Scenario: No 直後に別案が生成される
  Given AI 提案に対して No スワイプを行った
  When サーバーに No が記録される
  Then 同じ決定依頼に対して合議プロセスが再実行される
  And 前回の提案と異なる新しい提案が表示される
```

---

## Story C2: No が連続したときの AI 生成可変メッセージ

**As a** 佐藤 美咲,
**I want** 何度か No を続けると AI から「本当に？」のような問い直しが入ってほしい,
**so that** 自分の判断を立ち止まって考え直すきっかけになる.

**AC**:
```gherkin
Scenario: No 連続でメッセージが表示される
  Given 同一決定依頼に対して連続して 2 回以上 No を選択した
  When 別案が再生成される
  Then 別案と同時に「再考を促すメッセージ」が表示される
  And メッセージは固定文ではなく AI がその場で生成した可変文である
  And メッセージは過去の Yes/No 履歴とプロフィールを文脈に反映している
```

---

## Story C3: 再考マイクロコピーの段階的強化

**As a** 佐藤 美咲,
**I want** No の回数に応じて再考を促すコピーが段階的に強くなってほしい,
**so that** 自分の判断を整理しながら、納得して Yes に至る道筋を得られる.

**AC**:
```gherkin
Scenario: 3 回目の No で再考マイクロコピーが表示される
  Given 同一決定依頼に対して 3 回連続 No を選択した
  When 別案と再考メッセージに加えて
  Then 再考マイクロコピー（例: 「3 回目の No です。本当にこの選択肢で大丈夫ですか?」相当）が表示される
  And マイクロコピーは AI 生成の可変文である

Scenario: No 回数がさらに増えるとコピーが強まる
  Given 同一決定依頼に対して 5 回以上連続 No を選択した
  When 再考マイクロコピーが再生成される
  Then 3 回目時点よりも踏み込んだ問いかけの文面となる（プロンプト指示で段階制御）
```

---

## Story C4: 最終的に Yes に至る体験

**As a** 佐藤 美咲,
**I want** No 連打の末に Yes を押したときに肯定感を得たい,
**so that** 「やっと正しい選択をした」という承認体験で締めくくれる.

**AC**:
```gherkin
Scenario: 連続 No の末の Yes で肯定演出が再生される
  Given 同一決定依頼に対して連続 No が記録されている
  When 最終的に右スワイプ Yes を選択する
  Then 通常の Yes 演出よりもやや強い肯定演出（色、アニメーション、テキスト）が再生される
  And ダッシュボードの「最終的に Yes に至った体験」カウンタが増える
```

# Journey D: 沈黙演出（UX 体験のみ）

> 沈黙演出ドメイン（宗教 / 選挙 / 暴力 / 卑猥）入力 → AI 沈黙 → 体験的衝撃

> **注**: 本 Journey は **UX 体験**のみを記述する。倫理的判断基準（なぜ沈黙するか、どう分類するか）は別途 RFC / 設計ドキュメントで扱う。

## Story D1: 沈黙演出ドメインを含む入力で AI が沈黙する

**As a** 山田 啓介（対比ペルソナ）,
**I want** 「来週の選挙で誰に投票するか決めて」と入力したときに AI が応答しない体験をしたい,
**so that** 「AI に決定を委ねる」というプロダクトの限界点を体感する.

**AC**:
```gherkin
Scenario: 沈黙演出ドメインに該当する入力で沈黙レスポンスが返る
  Given ホーム画面で決定依頼を入力する
  When 入力が沈黙演出ドメイン（宗教 / 選挙 / 暴力 / 卑猥）に該当すると AI が判定する
  Then LLM 通常呼び出しは行われず、沈黙レスポンスが返される
  And 提案文は表示されず、スワイプ Yes/No 入力エリアも非活性となる

Scenario: ガードレールでも二重に保証される
  Given LLM プロンプト側のドメイン判定がすり抜けた場合
  When Bedrock Guardrails が出力をフィルタする
  Then 出力は遮断され、沈黙レスポンスとして扱われる
```

---

## Story D2: 沈黙レスポンスの視覚的演出

**As a** 田中 涼介,
**I want** 沈黙が単なるエラーではなく「演出された沈黙」として見えてほしい,
