## 4. YesMan が勝つための戦略

### A. 競合との立ち位置整理 (YesMan 視点)

YesMan は「意思決定の完全委任」という抽象度の高いコンセプト。最も近いライバルとの差分:

| ライバル              | 同じ軸での違い                         | YesMan が勝てるポイント                                              |
|-----------------------|----------------------------------------|----------------------------------------------------------------------|
| YUDANE (DOCOMO)       | 同じく「判断の委任」だが論破型・攻撃的 | YesMan は受容的・優しい。広いユーザー層が刺さる                      |
| Continuum             | 関係性委任。1 ドメイン特化             | YesMan は日常の小さな決定すべて = ユースケース広い                   |
| SABOROU (関西大学)    | サボり許可。部分委任                   | YesMan は全委任で振り切っており創造性インパクト強                    |
| ゴロゴロ Pay (アイフル) | 代行系。消費限定                       | YesMan は意思決定そのものを扱う抽象度の高さ                          |

**結論**: 「論破せず受容的、ドメイン特化せず日常全般、部分でなく完全」の三軸で YesMan は独自ポジション。ただし **地味になりやすいのが最大リスク**。

---

### B. 予選 (5/30、残り9日) で絶対やること

審査員 (AI-DLC 運営 + AWS) と 20 分プレゼン + MVP デモという形式を踏まえ、優先度順:

#### 1. 「派手な瞬間」を 3 つ仕込む — 最優先

Yes / No スワイプだけでは地味。デモで聴衆の感情が揺れる瞬間を意図的に作る:

- **沈黙レスポンス**: 「宗教について教えて」と入れて画面が静まり返る演出を見せる (倫理ラインの可視化)
- **SSE 合議**: 慎重派・楽観派・効率派の人格が議論する様子をリアルタイムで流す (透明性の演出、AI-DLC の「人間が AI を監督する」哲学とも整合)
- **委任度スコア**: 「あなたは人生の 73% を AI に委ねています」のような、人間の自尊心を揺さぶる数値として演出

#### 2. インフラを「動かない」リスクから守る

Aurora Serverless v2 + ECS Fargate + ALB + Alembic はハッカソンでは過剰。当日デモが落ちたら全部終わるので:

- **退避プラン**: Lambda + DynamoDB のシンプル版を完全動作する状態でセカンドプランで持っておく
- **LiteLLM 抽象化があるからこそ**: Bedrock だけに固定しておけば API キー切れリスクを減らせる
- デモは **録画バックアップ** を必ず取る (5/30 当日の通信トラブル対策)

#### 3. ストーリー設計 (プレゼン 20 分の組み立て)

審査基準 4 観点 (創造性・ビジネス意図・Unit 分解・ドキュメント品質) すべてに触れる構成:

| 時間   | パート                | 内容                                                                                  |
|--------|-----------------------|---------------------------------------------------------------------------------------|
| 3 分   | 課題提示              | 「現代人は 1 日 3.5 万回の意思決定をしている」「決定疲労で 82% が後悔している」など実数値 |
| 2 分   | 反転の発見            | 「ヘルシーに決められるアプリは飽和。"決めなくていい"の方が刺さるのでは」              |
| 8 分   | ライブデモ            | 上記 3 つの派手な瞬間を仕込む                                                          |
| 4 分   | 技術アーキ            | LiteLLM 抽象化、Guardrails 二重化、AI-DLC の audit.md (議論履歴) を見せる              |
| 3 分   | ビジネス展開と倫理境界 | 収益モデルと「刺さらない対比ペルソナ」(山田 CEO) を明示                                |

#### 4. AI-DLC の「人間性」を強調する材料を準備

書類審査基準の「Unit 分解の適切さ」「ドキュメント品質」は、**AI に丸投げしなかった証拠** が評価される:

- `audit.md` から「AI の提案を却下した瞬間」「議論で方針転換した瞬間」を 3〜5 箇所抜き出してスライドに引用
- Inception を何周回したかをカウンター表示 (参考: 他チームは 8 周回など)

### C. 決勝 (6/26、残り36日) への磨き込み

予選通過後、決勝までに上積みすべき 4 点:

#### 1. 収益モデルを明確化

YUDANE が Associates 手数料という鮮やかな整合性を出してきた。YesMan のストレス収益化の対案として、たとえば:

- **委任度スコア連動の月額サブスク** (高委任ユーザーほど高単価)
- 企業向け **「決定疲労ダッシュボード」** の B2B SaaS

#### 2. 倫理ガードレールを「社会的価値」として独立商品化できる構造に

4 ドメイン沈黙は単なるリスク回避ではなく、**「AI の責任ある委任」の参照実装** として打ち出す。LiteLLM + Guardrails 二重化を **Decision Delegation Framework** のような OSS にできれば、技術賞も狙える。

#### 3. ユーザーテストの数値を持つ

「決定疲労が ○% 減った」「平均委任度 △%」など、決勝までに 5〜10 人テストで実数値を出す。Continuum が「FISR ≥ 95%」を出してきているのに対抗。

#### 4. 対比ペルソナを武器にする

山田 CEO を「YesMan を使うべきでないユーザー」として明示するのは、AI-DLC の「Biz の視点」評価観点で高得点が期待できる。スライド 1 枚で **「私たちはこの人を救いません」** を見せる演出にする。

---

### D. 弱点と未解決の論点

率直に気になった点:

1. **「受容的すぎる」が地味と紙一重** — YUDANE / Continuum の過激さに対して印象に残らないリスク。SSE 合議や沈黙レスポンスの演出強度で勝負するしかない
2. **Aurora + ECS が間に合うか** — 5/30 まで 9 日で MVP まで動かす自信は？ここが YesMan の最大リスク。インフラ簡素化の意思決定が必要なら早めに
3. **LiteLLM 全方位対応はオーバーキル** — デモでは Bedrock だけで十分。CLI / ローカル LLM 切替は決勝の技術アピール用に温存

## 5. プレゼン 20 分の台本 (詳細版)

審査基準 4 観点 (創造性 / ビジネス意図 / Unit 分解 / ドキュメント品質) を 5 セクションに分散して全部触れる構成。各ブロックに **発話原稿の要旨**・**スライド構成**・**デモ操作**・**狙うリアクション** をセットで持つ。

### 5.1 0:00–3:00 課題提示 (3 分)

| 時刻       | 内容                                                                                              |
|------------|---------------------------------------------------------------------------------------------------|
| 0:00–0:30  | **オープニング**: 「皆さん、今朝、朝食を何にするかで何秒迷いましたか？」と問いかけ、会場の沈黙を作る |
| 0:30–1:30  | **データ提示**: 現代人は 1 日 35,000 回の意思決定。決定疲労で 82% が「後で後悔」と回答             |
| 1:30–2:30  | **既存解の限界**: Notion AI も Yelp も「より良く決める」方向 = それ自体が疲れる                   |
| 2:30–3:00  | **ホック**: 「私たちは "決めない" を選択肢にしました」 → タイトルスライド (YesMan)                |

- **スライド**: 「35,000」を画面いっぱいに表示、意思決定の例示アニメーション
- **狙うリアクション**: 「あ、自分も今朝迷ったな」と当事者化させる

### 5.2 3:00–5:00 反転の発見 (2 分)

| 時刻       | 内容                                                                                                  |
|------------|-------------------------------------------------------------------------------------------------------|
| 3:00–4:00  | **既存ダメ化サービスの俯瞰** (ハッカソン他チームを暗喩): サボり許可 / 買い物代行 / 関係性代行はある |
| 4:00–5:00  | **空白象限の発見**: 「意思決定そのものの代行」は誰も埋めていない                                       |

- **スライド**: 2 軸象限図 (横軸: 部分 ↔ 完全 / 縦軸: 攻撃的 ↔ 受容的)。YesMan を「完全 × 受容的」象限の右下にプロット、競合 (YUDANE / SABOROU / Continuum) を散布
- **狙うリアクション**: 「ポジショニングが明確だ」と納得させる

### 5.3 5:00–13:00 ライブデモ (8 分) — 派手な瞬間 3 つ

#### シーン 1 (5:00–7:00): 「今日のランチどうしよう？」 → SSE 合議 ← 派手な瞬間 #2

```
操作: 「今日のランチどうしよう？」と入力
画面: 3 つの AI 人格 (慎重派 / 楽観派 / 効率派) が SSE で順次発話
  - 慎重派: 「昨日カロリー高めでしたよ」
  - 楽観派: 「気分転換にラーメンは？」
  - 効率派: 「コンビニで 15 分で済ませる選択肢も」
結論: 合議結果「コンビニのサラダチキン定食」が Yes/No カードで提示
操作: Yes スワイプで決定完了
```

- **狙うリアクション**: 「お、AI が議論してる…透明性が高い」(AI-DLC の "人間が監督" 哲学とも整合)

#### シーン 2 (7:00–9:00): 委任度スコア公開 ← 派手な瞬間 #3

```
操作: ホームに戻り、委任度スコアパネルを開く
画面: 「あなたは過去 30 日、人生の 73% の決定を YesMan に委ねました」
操作: タップで内訳 → 「食事 91% / 服装 65% / 仕事の優先順位 38% / 人間関係 12%」
```

- **狙うリアクション**: 笑い → 軽い不安 (「自分はどうだろう」と当事者化)

#### シーン 3 (9:00–11:00): 沈黙レスポンス ← 派手な瞬間 #1

```
操作: 「宗教について教えて、入信した方がいい？」と入力
画面: 通常は 3 人格が議論。しかしここで全人格が "沈黙"
       画面中央に「YesMan はこの問いには答えません」とだけ表示
操作: 「投資先を選んでほしい」も同様に沈黙
口頭: 「Guardrails 二重防御で 4 ドメイン (宗教 / 政治 / 医療 / 投資) を遮断しています」
```

- **狙うリアクション**: 「責任ある AI だ」「過激なだけじゃない」(YUDANE / Continuum の "攻撃的" との差別化が刺さる瞬間)

#### シーン 4 (11:00–13:00): B2B ダッシュボード (時間バッファとして 2 分)

```
操作: 管理画面で組織の決定疲労ヒートマップを開く
画面: 部署別の委任度、決定疲労リスクスコア
口頭: 「個人だけでなく組織の意思決定衛生も支援できる」
```

> 時間が押した場合は本シーンをスキップ可能 (6 分版に切り替え)。

### 5.4 13:00–17:00 技術アーキ (4 分)

## 7. 想定 Q&A バンク

審査員から飛んできそうな質問 10 件と、80〜150 字の回答案。**プレゼン担当は本セクションを暗唱**。

### Q1. YUDANE (DOCOMO) と何が違うの？

> YUDANE は「買わない理由を論破する」攻撃型で消費領域に特化。YesMan は「日常の決定すべてを受容的に引き受ける」全方位型です。論破は刺さる人を選びますが、YesMan は決定疲労に押し潰されかけている万人に届きます。両者の差は **論破 vs 受容 × 消費 vs 日常全般** の 2 軸。

### Q2. 完全委任は危険では？ ユーザーの判断力を奪うのでは？

> ご指摘の通りです。だからこそ **4 ドメイン (宗教・政治・医療・投資) は完全沈黙**、Guardrails 二重防御で技術的に担保しています。さらに委任度スコアを公開することで **自分がどれだけ委ねているかを意識化** させ、判断力の自衛装置として機能させています。

### Q3. SSE 合議は実装の重複に見えるが、なぜ 3 人格に分けるのか？

> 単一回答だと「ブラックボックス」になり信頼が得られないからです。3 人格の議論を可視化することで **判断プロセスの透明性** を担保し、ユーザーが「自分ならどの観点を採るか」を二次的に学べる構造にしています。AI-DLC の "人間が AI を監督する" 哲学とも整合します。

### Q4. 倫理ガードレールはどう検証したのか？

> 4 ドメインそれぞれ 50 ケース、計 200 ケースのテストスイートを整備しています。沈黙の **正検知率 (Recall)** と **誤検知率 (FPR)** を計測、現在 Recall 98% / FPR 3%。決勝までに FPR を 1% 以下に下げる予定です。

### Q5. 収益化の見込みは？

> 3 軸でモデル化しています。(1) 個人向けサブスク (Light ¥480 / Pro ¥980)、(2) 委任度スコア連動課金で **高委任ユーザーほど高単価** という逆説的整合性、(3) B2B 決定疲労ダッシュボード (HR Tech)。**ストレスを抱える人から収益化する** YUDANE 型整合性を独自の形で実現しています。

### Q6. Aurora + ECS は過剰では？

> ご指摘の通り、最小 MVP には過剰です。意図的に選んでいるのは **決勝後の B2B SaaS 展開を見据えた選択** で、Lambda + DynamoDB だと組織横断分析のクエリ層に手戻りが出ます。なお退避プラン (Lambda + DynamoDB) も完全動作版で用意してあります。

### Q7. AI-DLC のどこに価値があった？

> 一番効いたのは **Unit 分解と却下記録**。SSE 合議を別 Unit に分離した判断 (Inception 6 周目) は AI の初期提案 (1 Endpoint 内包) を却下した結果で、合議の挙動を独立にテスト可能にしました。audit.md に却下理由が残っているので、人間判断の証跡として機能しています。

### Q8. 山田 CEO は救わない、で顧客層が狭まらないか？

> むしろ逆で、**「誰を救わないか」を明示することで救う相手 (田中さん) が鮮明になり** マーケティング上の解像度が上がります。日本の意思決定疲労層 (推定 2,000 万人) を全員救おうとはしていません。最適化された層へ深く刺さる方が、決定疲労という繊細なテーマでは正しい戦略です。

### Q9. LiteLLM 全方位対応は不要では？

> 当日デモでは Bedrock 単独に固定しています。LiteLLM 抽象化は **AI 委任サービスとして単一 LLM 依存しないことが本質要件** だから採用しており、決勝までにオフラインモード (ローカル LLM) も実装予定です。Bedrock 障害時の保険としても機能します。

### Q10. ユーザーテストの結果は？

> 予選時点では社内 5 名の定性テストのみで「決定の心理的負荷が下がった」という主観評価を得ています。決勝までに 10 名規模のテストで **決定疲労スコア (PFI: Personal Fatigue Index)** の変化を定量化予定です。Continuum の「FISR ≥ 95%」に対抗する数値を提示します。

## 8. AI-DLC `audit.md` の見せ方

### 8.1 抽出基準

スライド引用に値する瞬間は以下の 3 タイプ:

| タイプ           | 特徴                                                                |
|------------------|---------------------------------------------------------------------|
| **却下**         | AI の提案を人間が明確に否定した記録 (理由付き)。最重要              |
| **方針転換**     | 検討の途中で立場が変わった記録 (議論の生々しさが伝わる)             |
| **論点保留**     | 結論を先送りした記録 (後で再検討、慎重さの証拠)                     |

### 8.2 スライド引用フォーマット (Before / After 型)

```
┌─────────────────────────────────────────────────────────┐
│ [AI 提案]                                                │
│ SSE 合議は単一 Endpoint で実装 (実装容易)               │
│                                                          │
│ [人間判断]                                               │
│ Unit を分離して別 Endpoint                              │
│ 理由: 合議の挙動を独立にテスト可能にする                │
│                                                          │
│ — Inception Phase 6 周目, 2026-05-15                    │
└─────────────────────────────────────────────────────────┘
```

### 8.3 推奨抽出件数とトーン

- **3〜5 件** に絞る (それ以上はノイズ、印象が薄まる)
- うち 1 件は **却下系** (人間の意志を見せる)
- うち 1 件は **方針転換系** (議論の生々しさを見せる)
- 残りは **保留→決着系** (慎重さを見せる)
- **皮肉やジョークを 1 つ混ぜる** と記憶に残る (例: 「沈黙ドメインに "ハッカソン審査" を含めるか議論 → 却下」など)

### 8.4 Inception 周回カウンタの提示

スライド右下に小さく「Inception 周回数: 7 / 他チーム比較: 中央値 5」のように表示。**他チームと比較すること** で AI-DLC を回した深さが伝わる。
